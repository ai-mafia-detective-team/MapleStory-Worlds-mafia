# 비공개 출시 테스트 결과 및 P0 수정 계획

비공개 출시 멀티플레이 테스트에서 확인된 문제와 P0 수정 계획, 담당자별 작업 경계를 정리한 문서입니다.

이 문서는 현재 구현과 테스트 결과를 구분해 기록합니다. 현재 코드에 없는 기능은 구현된 것처럼 표현하지 않습니다.

## 1. 상태 표기 기준

- **[현재]** 현재 코드에 이미 구현된 내용
- **[문제]** 실제 멀티플레이 테스트에서 확인된 현상
- **[계획]** 앞으로 구현하거나 변경할 내용
- **[논의]** 팀 합의가 필요한 내용

## 2. P0 — 실제 테스트 확인 문제

P0에는 비공개 출시 테스트에서 실제로 확인된 문제만 포함합니다.

1. **[문제]** `LuaTableToJsonType.UnknownType` 서버 오류
2. **[문제]** 방 퇴장·삭제 후 목록 동기화 실패
3. **[문제]** 퇴장한 참가자가 기존 방과 새 방에 남는 현상
4. **[문제]** 준비 상태가 다른 사용자에게 표시되지 않음
5. **[문제]** 게임 진행 중 처음 도달한 밤에 역할 행동 UI가 표시되지 않음
6. **[문제]** 게임 종료 후 승리 화면과 게임 상태가 초기화되지 않음
7. **[문제]** 같은 방에서 두 번째 게임 시작 시 이전 결과 화면이 남음

## 3. P0에서 제외하는 항목

다음 항목은 P0 실제 확인 문제와 분리합니다.

### P1 — 핵심 사용성

- **[계획]** 채팅 발신자 표시
- **[계획]** 게임 종료 후 대기실 복귀 UX 정리
- **[계획]** 수사방 찾기 상태·입장 버튼 구조 개선
- **[논의]** 방장 퇴장 정책 전체
- **[논의]** 재접속 정책

> 퇴장·연결 종료로 유령 참가자가 남는 P0 현상을 해결하기 위한 최소 정리는 P0에 포함할 수 있습니다. 방장 위임, 재접속 복원 등 전체 정책은 별도 논의 후 진행합니다.

### P2 — 완성도

- **[계획]** 봇 이름 변경
- **[계획]** UI 버튼 위치 세부 조정
- **[계획]** 준비 완료 시각 효과
- **[계획]** 상태별 안내 메시지
- **[계획]** 게임 결과 화면 개선

        ↓

## 6. 노형래 — 로비 및 방 Registry

### 담당 범위

- **[현재]** `InvestigationRoomManager.mlua`의 방 Registry
- **[현재]** `LobbyController.mlua`의 로비 버튼과 방 생성·검색 기능 연결
- **[현재]** 방 생성·검색·입장·퇴장
- **[현재]** 빠른 입장과 대기실 진입 연결
- **[계획]** Registry 직렬화 오류 수정
- **[계획]** 퇴장·삭제·유령 참가자 및 방 목록 동기화 수정
- **[계획]** 빈 방 제거와 참가자 수·방 상태 동기화

### P0 작업

1. **[문제]** `WriteRegistrySnapshot()` 저장 과정에서 `LuaTableToJsonType.UnknownType` 오류 발생
2. **[계획]** SharedMemory에 저장할 데이터를 직렬화 가능한 값만 포함한 DTO로 변환
3. **[문제]** 삭제하거나 퇴장한 방·참가자가 검색 목록과 새 방에 남음
4. **[계획]** `roomId` 단위로 방 상태를 독립 관리하고 입·퇴장 후 Registry를 즉시 갱신
5. **[계획]** 빈 방과 유효하지 않은 참가자 정리

### 담당 종료 지점

```text

→ 방 선택
→ 입장 검증
→ 해당 수사방 대기실로 이동
```

대기실 이동 이후 참가자 슬롯, 준비 상태와 게임 시작 판정은 이지건이 담당합니다.

- `RootDesk/MyDesk/Lobby/LobbyController.mlua`
- `RootDesk/MyDesk/NicknameSetupController.mlua`

### 수사방 찾기 UI 연결 원칙

- 노형래는 `.ui` 엔티티를 생성하지 않습니다.
- 노형래는 `.ui` 엔티티 이름을 변경하지 않습니다.
- 노형래는 UI 위치·크기·이미지를 변경하지 않습니다.
- 필요한 UI 구조 변경은 김도하에게 요청합니다.

## 8. 현재 공개 방 DTO

### [현재] `ToPublicRoom()` 반환 필드

`RootDesk/MyDesk/Room/InvestigationRoomManager.mlua`의 `ToPublicRoom()`은 다음 필드를 반환합니다.

```text
roomId
roomName
mode
hostUserId
hostNickname
currentPlayers
maxPlayers
status
isPrivate
hasPassword
createdAt
```

### [현재] 공개 DTO에 없는 필드

다음 필드는 현재 공개 DTO에 포함되어 있지 않습니다.

```text
players
localUserId
ownerUserId
roomTitle
roomStatus
currentPlayerCount
```

### [계획] 대기실 연결 정보 확장

대기실 연결에 추가 정보가 필요하면 기존 공개 DTO 확장 또는 별도 조회 API를 설계합니다. 현재 공개 DTO에는 참가자 상세 목록과 `localUserId`가 포함되어 있지 않습니다.

새 DTO의 필드와 소유권은 노형래·이지건이 인터페이스를 합의한 뒤 확정합니다.

## 9. 현재 Registry API

### [현재] 구현된 API

```text
JoinRoom(roomId, password)
LeaveRoom(roomId)
UpdateRoomStatus(roomId)
```

- 서버 사용자 식별은 별도 `userId` 매개변수가 아니라 `senderUserId`를 사용합니다.
- `JoinRoom(roomId, userId)`와 `LeaveRoom(roomId, userId)` 형태는 현재 API가 아닙니다.

### [계획] 필요 시 설계할 API

다음 이름은 현재 구현된 API가 아니라 향후 인터페이스 후보입니다.

```text
GetRoomSnapshot
UpdateReadyState
RemoveDisconnectedPlayer
```

구체적인 시그니처와 ExecSpace는 담당자 합의 후 결정합니다.

## 10. 준비 상태 소유권

- **[현재]** 준비 상태의 원본은 `RootDesk/MyDesk/Mafia/MafiaGameLogic.mlua`가 관리합니다.
- **[현재]** 준비 변경은 `MafiaGameLogic:SetReady()`에서 처리합니다.
- 노형래는 방 Registry와 생성·검색·입장·퇴장을 담당합니다.
- 이지건은 대기실 참가자 표시, 준비 상태, 시작 판정과 게임 진행을 담당합니다.
- **[논의]** 검색 목록이나 Registry에도 준비 상태 요약이 필요하다면 두 담당자가 갱신 인터페이스를 합의합니다.
- 준비 상태의 원본을 `InvestigationRoomManager`에 중복 구현하지 않습니다.

## 11. 현재 게임 진행 순서

### [현재] 게임 시작 흐름

```text
게임 시작
→ 낮 토론
→ 투표
→ 첫 번째 밤
```

게임은 밤이 아니라 낮 토론으로 시작합니다. P0의 밤 UI 문제는 “게임 시작 직후”가 아니라 **게임 진행 중 처음 도달하는 밤의 역할 행동 UI** 문제를 의미합니다.

## 12. 게임 시작 정책 — 팀 논의 필요

### [현재] 구현

```text
모든 접속자 준비 완료
→ 자동 3초 카운트다운
→ 자동 게임 시작
```

### [논의] 가능한 대안

- 전원 준비 완료 후 자동 시작 유지
- 전원 준비 완료 후 방장이 시작 버튼 클릭

방장만 시작 버튼을 사용하거나 방장이 직접 시작하는 규칙은 현재 구현된 규칙이 아닙니다. 정책이 확정되기 전까지 P0 구현 항목으로 처리하지 않습니다.

정책이 변경되면 `Docs/GameFlow.md`와 실제 코드를 함께 갱신합니다.

## 13. UI 파일 소유권

### [현재] 공식 규칙

현재 `TEAM_RULES.md`가 공식 규칙이며, 모든 `.ui` 파일은 김도하만 수정합니다.

공식 규칙 개정 전:

- 이지건은 `.ui` 파일을 직접 수정하지 않습니다.
- 필요한 UI 엔티티와 경로 변경을 김도하에게 요청합니다.
- 이지건은 관련 `.mlua` 기능만 수정합니다.

### [논의] 규칙 개정 후 가능한 구조

| 구간 | UI 담당 |
|---|---|
| 수사방 입장 전 | 김도하 |
| 수사방 입장 후 | 이지건 |

팀이 `TEAM_RULES.md`를 공식적으로 변경하기 전까지는 기존 규칙이 우선입니다.

UI 엔티티 경로·이름은 스크립트 연결 계약이므로 변경 전에 관련 담당자에게 공유합니다. `.ui` 충돌은 raw JSON이나 충돌 마커를 직접 편집해 해결하지 않습니다.

## 15. P0 완료 기준

최소 2명 이상의 실제 클라이언트로 다음 시나리오를 통과해야 합니다.

1. 방 생성
2. 다른 사용자 입장
3. 준비·취소 상태가 모든 클라이언트에 동기화
4. 퇴장 후 슬롯과 검색 목록에서 즉시 제거
5. 재입장해도 유령 참가자가 남지 않음
6. 게임 시작 후 낮 토론과 투표 진행
7. 게임 진행 중 처음 도달한 밤에 역할 행동 UI 정상 표시
8. 게임 종료 후 준비·역할·생존·투표·밤 행동·승리 화면 초기화
9. 같은 방에서 두 번째 게임 정상 진행

## 16. Git 및 검증 규칙

- 작업 시작 전 각자 브랜치에 최신 `origin/develop`을 반영합니다.
- 담당 파일이 겹치면 병합 전에 먼저 조율합니다.
- 커밋은 기능 단위로 짧게 나눕니다.
- 화면 전환이나 게임 진행 규칙을 바꾸면 `Docs/GameFlow.md`도 갱신합니다.
- Maker에서 `stop → refresh → build logs → play → runtime logs` 순서로 검증합니다.
- PR 본문에 테스트 시나리오, 결과와 남은 문제를 기록합니다.
